# 0005 · 鉴权姿态与端口隔离边界

- **状态**：已裁决 / Accepted（2026-11-12 补记为架构决策；依据 2026-10-25 第三轮裁决 ⑫ 与 `SVC-STRAT-G1` 的已落地实现。**2026-11-12 裁决 A**：5 条公开写端点收紧为 `service` 闸，分两步落——**两步均已落地**：agent 侧带 token 能力先发布（`tellurion-agent@a59631e`），随后本仓把 5 条写端点并入 `servedPolicy`（见 Consequence 1））
- **场景（Context）**：
  - 本仓是**单人自托管**的策略资产服务（定义 / 版本 / artifact / resolve / promote 审计）。调用方只有两类：agent 或操作者（按 ADR-0004 **直连**本仓）与编译进程；没有浏览器或终端用户面，也没有账户 / 资金类数据。
  - `SVC-STRAT-G1`（2026-11-07）之前，`internal/httpapi` 的路由**全部无保护**。G1 引 kit `auth/httpadapter` 后，裁决 ⑫ 先只给 **3 条**端点挂了鉴权闸，其余保持公开，边界交给端口隔离。
  - **协议事实（实测，2026-11-12 收紧后复核 `internal/httpapi/api.go:112-133` 与 `internal/httpapi/policy.go:20-29`）**：13 条业务端点 = **8 条受保护写**（5 条资产写 + `promote` + 2 条 `/internal/*`）+ **5 条公开读**（`versions` / `promotions` / `builds/{job_id}` / `resolve` / `artifact`）。写侧已无公开端点；`api-schema` 早期"10 条公开端点"的表述指收紧前的姿态，已被本次修订取代。
  - kit 提供的是 JWT 机制（签发 / 验签 / `DecideStartup` / 角色词表），不是鉴权姿态；姿态必须由使用方自己裁决并留档，否则半年后只剩 `api-schema` 的行为表，没人知道"为什么有 8 条挂闸、5 条公开"。

- **决策（Decision）**：
  1. **当前姿态：5 条读端点公开，8 条写端点一律过 `role=service` 闸**。默认监听 `127.0.0.1:8090`；容器内绑 `0.0.0.0`（容器必须如此）但只在宿主回环发布（`deploy/compose.yaml` 的 `127.0.0.1:8090:8090`），集群内只经 ClusterIP 提供服务。公开的只有读面（`versions` / `promotions` / `builds/{job_id}` / `resolve` / `artifact`），它们不带写入能力，靠端口隔离兜底；写面（create / source / build / validate / deprecate / promote + 2 条 `/internal/*`）没有身份一律拒绝。**读公开的理由不适用于写**（见理由第 1 条）；跨仓发布顺序（agent 先具备带 token 能力、本仓后收紧）见 `docs/TASKS.md` 的 `STRAT-WRITE-AUTH-ROLLOUT` 归档记录。
  2. **8 条端点只认 `role=service`**（`internal/httpapi/policy.go:20-29` 的 `servedPolicy`）：5 条资产写（`POST /api/strategies`、`PUT /api/strategies/{id}/source`、`POST /api/strategies/{id}/build`、`POST /api/strategies/{id}/versions/{hash}/validate`、`POST /api/strategies/{id}/versions/{hash}/deprecate`）、`POST /api/strategies/{id}/versions/{hash}/promote`、`POST /internal/strategies/{id}/artifacts`、`POST /internal/strategies/{id}/builds/{job_id}`。凭证 = kit `IssueServiceToken` 签发的长期 **access** token（`role=service`）。无 token / 坏 token / refresh token → 401 `unauthenticated`；角色不符 → 403 `forbidden`。本仓是**验签方**，不持有、不签发、不存储 token。
  3. **启动闸 = kit `DecideStartup` 的 fail-closed 判据**：有 `JWT_SECRET` → 开鉴权；无 secret + 回环绑定 → 开放访问；无 secret + 非回环 + `AUTH_INSECURE_EXPOSURE=loopback-published` → 开放访问（容器形态）；**其余一律拒绝启动**（含拼错 / 空 / 部分声明）。不会出现"漏配 secret 就全开"的进程。
  4. **promote 额外要求受信头 `X-Actor`**：由 agent / 操作者直连本仓时携带（ADR-0004 对本仓不代理 promote 的裁决）；缺失 → 400 `actor_required` 且**不写审计行**；成功 → 追加一行 `strategy.strategy_promotions`（actor / decided_at / outcome）；审计写失败 → 500 `audit_failed`。
  5. **限流按身份分桶**（50 rps / 突发 200），未鉴权端点共用 `open-access` 桶；**鉴权先于限流**——401 / 403 不会被 429 顶替。探针 `/healthz` `/readyz` 不鉴权、不限流（被限流会被编排层读成坏实例）。

- **理由（为什么是它而不是别的）**：
  - **为什么不给 5 条读端点发 token**：kit 没有 token 注册表、没有吊销列表、没有服务注册表；单人自托管下给每条读端点签 token 只增加运维面，不增加真实安全性。这些端点的数据是策略定义与构建状态，不是账户 / 资金面；唯一现实威胁是**端口越界暴露**，用"启动闸 + 发布层回环 / ClusterIP"可以机械校验。**这条理由只覆盖读侧**：写操作需要身份与可审计的调用方，已于 2026-11-12 收紧（见 Consequence 1），不受本条豁免。
  - **为什么写闸只认 `service` 不认 user**：八条受保护端点的调用方是资产登记链（agent copilot）、编译进程与 agent / 操作者，没有终端用户 JWT；角色词表在 kit `auth.ServiceRole`（`service`），本仓不新造角色。service token 的 subject 是 caller 自选的 `service:<name>`（非数字），kit 在 API 边界对 service 角色豁免 int64 subject 校验，这是既有约定不是本仓发明。
  - **为什么 `X-Actor` 用受信头而不是签名身份**：审批人身份由**直连方**携带（裁决 ⑫ 按部署入口解释，ADR-0004）；本仓只记录、不猜审批人，也不做"caller 自报 + 本仓核实"的伪校验。伪造门槛 = 持有 service token。
  - **为什么不做 per-endpoint RBAC**：策略表只有一张（`servedPolicy`），新增受保护端点会让 `TestServedPolicyIsServiceOnly` 与守卫测试一起红——那是**刻意设计的变更闸门**：想放开或收紧必须先改文档与用例，不许悄悄改。

- **代价 / 后果（Consequences）**：
  1. **写侧缺口已闭合（2026-11-12）**：5 条资产写端点（create / source / build / validate / deprecate）已并入 `servedPolicy`（`internal/httpapi/policy.go:20-29`），路由侧由 `openRoute` 改为 `requireAuth`（`internal/httpapi/api.go:117-125`）。落地顺序按跨仓两步走执行：agent 侧 `StrategyAssetConfig.Token` + `call()` 发 `Authorization` 先发布（`tellurion-agent@a59631e`），本仓随后收紧，中间不留断链窗口。公开面只剩 5 条读端点，端口越界暴露的影响面从"可改资产"降为"可读资产"。
  2. **写操作现在的身份是 `service:<name>`，仍不是人类 actor**：审计主体仍只在 promote（`strategy_promotions`）。5 条资产写端点由 service token 标识调用方，但**不写审计行**——它们没有审批语义；人类审批人只在 promote 的 `X-Actor` 里出现。查询侧不能把 service 调用读成人工审批。
  3. **本地直跑没有"无 secret 放行写端点"的后门**：`DecideStartup` 的回环 / `AUTH_INSECURE_EXPOSURE=loopback-published` 豁免只决定**进程能否启动**，不会让受保护路由放行——无 authorizer 时受保护路由一律 503 `auth_unavailable`（`internal/httpapi/auth.go:87-92`）。因此本地起服务必须先由 core 仓 `tools/issue_service_token.go` 签发 token，并注入 `JWT_SECRET` + `STRATEGY_ASSET_TOKEN`（做法见 `docs/runbook.md`），按 fail-closed 处理。
  4. `X-Actor` 是 caller 自报的受信头，不是签名身份；信任模型依赖"只有 agent / 操作者持有 service token"。
  5. 无吊销：service token 长期有效，轮换只能靠换 `JWT_SECRET`（会让所有 token 立即失效）。
  6. 机械检查：`internal/httpapi/g1_test.go` 的策略表守卫 `TestServedPolicyIsServiceOnly`（8 条、只认 `service`）、读面公开钉子 `TestReadRoutesRemainPublic`、写侧判据 `TestWriteRoutesRejectBadToken` / `TestWriteRoutesAcceptServiceToken` / `TestProtectedRoutesRejectMissingToken` / `TestProtectedRoutesRejectNonServiceRole`，401 / 403 / 400 `actor_required` / 503 `auth_unavailable` 全覆盖；启动闸用例在 kit `auth/httpadapter`。

- **与 kit JWT 及其他仓的关系**：
  - kit 只提供**机制**：token 签发 / 验签、`DecideStartup` 启动闸、角色词表。**本 ADR 裁的是本仓的姿态**，不产出"所有服务统一鉴权"的结论，也不要求其他仓跟随。
  - 与 broker 仓的鉴权姿态**不统一**：broker 的写侧静态 token、读侧开放是它自己的分叉例外，已/应在**其本仓 ADR** 中单独记录。本 ADR 不覆盖、不声称与之一致；跨服务的凭证签发与角色口径归 core / kit 的既有文档。
  - 与 [ADR-0004](0004-core消费边界与promote归属.md) **互补**：0004 裁 promote 归属与"部署入口"解释，本 ADR 裁鉴权边界、启动闸与 `X-Actor` 的落点。
  - 行为表（每条端点的 401 / 403 / 400 语义）留在 [`../api-schema.md`](../api-schema.md) 的「鉴权与限流」节，本 ADR 只写"为什么这么定"，不抄表。

- **替代关系**：无。本 ADR 最初是 `SVC-STRAT-G1` 姿态的**补记**；2026-11-12 按裁决 A 两步走把写侧收紧（agent 先发布带 token 能力，本仓后收紧），本轮同时把"3 条受保护 / 10 条公开"修订为"8 条受保护 / 5 条公开读"。
