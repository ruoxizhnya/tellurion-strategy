# 0005 · 鉴权姿态与端口隔离边界

- **状态**：已裁决 / Accepted（2026-11-12 补记为架构决策；依据 2026-10-25 第三轮裁决 ⑫ 与 `SVC-STRAT-G1` 的已落地实现）
- **场景（Context）**：
  - 本仓是**单人自托管**的策略资产服务（定义 / 版本 / artifact / resolve / promote 审计）。调用方只有两类：agent 或操作者（按 ADR-0004 **直连**本仓）与编译进程；没有浏览器或终端用户面，也没有账户 / 资金类数据。
  - `SVC-STRAT-G1`（2026-11-07）之前，`internal/httpapi` 的路由**全部无保护**。G1 引 kit `auth/httpadapter` 后，裁决 ⑫ 只给 **3 条**端点挂了鉴权闸，其余保持公开，边界交给端口隔离。
  - **协议事实（实测，2026-11-12 复核 `internal/httpapi/api.go:112-133`）**：13 条业务端点 = **3 条受保护**（`promote` + 2 条 `/internal/*`）+ **10 条公开**。10 条公开里 **5 条是读**（`versions` / `promotions` / `builds/{job_id}` / `resolve` / `artifact`），**5 条是写**（create / source / build / validate / deprecate）。台账里"10 条读端点"是简称，**不是事实**——写侧公开端点属于下述"残余风险"，本 ADR 如实记录，不粉饰。
  - kit 提供的是 JWT 机制（签发 / 验签 / `DecideStartup` / 角色词表），不是鉴权姿态；姿态必须由使用方自己裁决并留档，否则半年后只剩 `api-schema` 的行为表，没人知道"为什么 10 条端点不挂闸"。

- **决策（Decision）**：
  1. **10 条公开端点不挂鉴权，边界 = 端口隔离**：默认监听 `127.0.0.1:8090`；容器内绑 `0.0.0.0`（容器必须如此）但只在宿主回环发布（`deploy/compose.yaml` 的 `127.0.0.1:8090:8090`），集群内只经 ClusterIP 提供服务。公开端点不区分 caller 身份。
  2. **3 条端点只认 `role=service`**（`internal/httpapi/policy.go` 的 `servedPolicy`）：`POST /api/strategies/{id}/versions/{hash}/promote`、`POST /internal/strategies/{id}/artifacts`、`POST /internal/strategies/{id}/builds/{job_id}`。凭证 = kit `IssueServiceToken` 签发的长期 **access** token（`role=service`）。无 token / 坏 token / refresh token → 401 `unauthenticated`；角色不符 → 403 `forbidden`。本仓是**验签方**，不持有、不签发、不存储 token。
  3. **启动闸 = kit `DecideStartup` 的 fail-closed 判据**：有 `JWT_SECRET` → 开鉴权；无 secret + 回环绑定 → 开放访问；无 secret + 非回环 + `AUTH_INSECURE_EXPOSURE=loopback-published` → 开放访问（容器形态）；**其余一律拒绝启动**（含拼错 / 空 / 部分声明）。不会出现"漏配 secret 就全开"的进程。
  4. **promote 额外要求受信头 `X-Actor`**：由 agent / 操作者直连本仓时携带（ADR-0004 对本仓不代理 promote 的裁决）；缺失 → 400 `actor_required` 且**不写审计行**；成功 → 追加一行 `strategy.strategy_promotions`（actor / decided_at / outcome）；审计写失败 → 500 `audit_failed`。
  5. **限流按身份分桶**（50 rps / 突发 200），未鉴权端点共用 `open-access` 桶；**鉴权先于限流**——401 / 403 不会被 429 顶替。探针 `/healthz` `/readyz` 不鉴权、不限流（被限流会被编排层读成坏实例）。

- **理由（为什么是它而不是别的）**：
  - **为什么不给 10 条公开端点发 token**：kit 没有 token 注册表、没有吊销列表、没有服务注册表；单人自托管下给每条读端点签 token 只增加运维面，不增加真实安全性。这些端点的数据是策略定义与构建状态，不是账户 / 资金面；唯一现实威胁是**端口越界暴露**，用"启动闸 + 发布层回环 / ClusterIP"可以机械校验。
  - **为什么写闸只认 `service` 不认 user**：三条受保护端点的调用方是编译进程与 agent / 操作者，没有终端用户 JWT；角色词表在 kit `auth.ServiceRole`（`service`），本仓不新造角色。service token 的 subject 是 caller 自选的 `service:<name>`（非数字），kit 在 API 边界对 service 角色豁免 int64 subject 校验，这是既有约定不是本仓发明。
  - **为什么 `X-Actor` 用受信头而不是签名身份**：审批人身份由**直连方**携带（裁决 ⑫ 按部署入口解释，ADR-0004）；本仓只记录、不猜审批人，也不做"caller 自报 + 本仓核实"的伪校验。伪造门槛 = 持有 service token。
  - **为什么不做 per-endpoint RBAC**：策略表只有一张（`servedPolicy`），新增受保护端点会让 `TestServedPolicyIsServiceOnly` 与守卫测试一起红——那是**刻意设计的变更闸门**：想放开或收紧必须先改文档与用例，不许悄悄改。

- **代价 / 后果（Consequences）**：
  1. **残余风险（明写，不隐藏）**：5 条公开**写**端点（create / source / build / validate / deprecate）在端口隔离失效时（误发布到 `0.0.0.0`、NodePort、ingress）会对任何网络可达者完全开放；启动闸**只拦"无 secret"组合**，拦不住"有 secret 但 10 条公开端点仍公开"。缓解 = 部署层必须保持回环 / ClusterIP。**若要求这些端点也需身份，先改 `policy.go` 策略表与本文档并另立单；本轮不改代码。**
  2. 公开端点的写操作**不留 actor**：审计主体只在 promote（`strategy_promotions`）。这是"公开 = 无身份"的直接后果，查询侧不能假设每条变更都有审计行。
  3. `X-Actor` 是 caller 自报的受信头，不是签名身份；信任模型依赖"只有 agent / 操作者持有 service token"。
  4. 无吊销：service token 长期有效，轮换只能靠换 `JWT_SECRET`（会让所有 token 立即失效）。
  5. 机械检查：`internal/httpapi/policy_test.go`（策略表守卫）、`internal/httpapi/g1_test.go`（401 / 403 / 400 `actor_required` / 503 `auth_unavailable`）、启动闸用例在 kit `auth/httpadapter`。

- **与 kit JWT 及其他仓的关系**：
  - kit 只提供**机制**：token 签发 / 验签、`DecideStartup` 启动闸、角色词表。**本 ADR 裁的是本仓的姿态**，不产出"所有服务统一鉴权"的结论，也不要求其他仓跟随。
  - 与 broker 仓的鉴权姿态**不统一**：broker 的写侧静态 token、读侧开放是它自己的分叉例外，已/应在**其本仓 ADR** 中单独记录。本 ADR 不覆盖、不声称与之一致；跨服务的凭证签发与角色口径归 core / kit 的既有文档。
  - 与 [ADR-0004](0004-core消费边界与promote归属.md) **互补**：0004 裁 promote 归属与"部署入口"解释，本 ADR 裁鉴权边界、启动闸与 `X-Actor` 的落点。
  - 行为表（每条端点的 401 / 403 / 400 语义）留在 [`../api-schema.md`](../api-schema.md) 的「鉴权与限流」节，本 ADR 只写"为什么这么定"，不抄表。

- **替代关系**：无。本 ADR 是既有 `SVC-STRAT-G1` 姿态的**补记**，不改任何鉴权代码与策略表。
